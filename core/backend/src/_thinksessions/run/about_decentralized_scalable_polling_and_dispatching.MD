## Fundamental truths heard by a highest-façade frontend

> **One-by-one E2E fact box**
>
> 1. Canonical `event_seq` is session-local, strictly increasing, and immutable.
> 2. A successfully recorded controller start is closed by one matching end for
>    every ordinary in-process `Exception`, subject to the explicit sink/crash
>    exclusions below.
> 3. Start and end share `dispatch_id`; every event has its own `event_id`.
> 4. Controller start and end carry the immutable dispatch actor:
>    `dispatcher_identity_id` and `dispatcher_role`.
> 5. Controller start and end carry complete canonical `U` and timestamps.
> 6. Datum lifecycle and external events are informative and need not carry
>    `U`, `dispatch_id`, or dispatch actor identity.
> 7. The latest complete frontend state is `U` from the latest controller event.
> 8. Semantic rejection is a successful end with `result.last_error`; systematic
>    failure is an end with `outcome="system_error"`.
> 9. Undo moves backward on the program tape but forward in canonical event time.
> 10. Incremental page replay and one-shot replay produce the same frontend
>     projection for the same retained event window.
> 11. The live queue is bounded; durable full history is a hosting concern.
> 12. Hosting exposes a first-class, run-level epsilon (`eps`) channel via
>     `threaded_callbacks`, ordered by run-scoped `eps_seq`, carrying causal
>     lineage (`theta_event_seq_at_emit`, `emitter_origin`, `trident_dispatch_id`)
>     and independent of canonical `event_seq` (`theta`).
> 13. Widgets emitting owner-only audit/economics messages may pass
>     `record_in_session_queue=False` on `emit(...)` so `explosion_events_callback`
>     receives the emission without entering the bounded canonical `_session_events_v1`
>     queue or advancing `event_seq`.

## Decentralized polling and dispatch

```text
Dispatcher–poller
decentralized canonical belief: C
decentralized epsilon cursor:   E

Canonical enquiry cadence:
    baseline B = 30 s

    local dispatch mode:
        D = 5 s
        active while a local dispatch is unresolved
        and for WD = 60 s after it resolves

    foreign/unknown activity mode:
        R = 15 s
        active for WR = 60 s after canonical movement
        attributable to another or unknown actor

    precedence:
        local dispatch mode
        > foreign/unknown activity mode
        > baseline

    expiry:
        return directly to baseline
        no exponential decay

Canonical (theta) loop:
    enquire latest canonical integer A

    A == C
        -> no pull

    A > C
        -> pull bounded pages after C
        -> apply in canonical order
        -> C := next_after_event_seq
        -> continue until C == A

Dispatch:
    dispatch(..., my_current_event_seq_number=C)

Run-level epsilon (eps) loop:
    cadence coupled to theta:
        250 ms while a local dispatch is in flight
        piggybacks on every theta poll tick otherwise
    reads /eps/?after_seq=E&limit=L
    eps_seq only (run-level, append-only)
    never changes C or Q
```

A successful canonical catch-up has already drained the high-water visible at
that moment. It therefore does not justify a subsecond canonical polling loop.
A modest 15-second window is useful only as a bounded prediction that another
actor may produce a nearby subsequent action.

A local dispatch is a stronger signal. It receives a 5-second canonical mode,
while the epsilon (`eps`) loop runs at 250 ms while a local dispatch is in
flight and piggybacks on every canonical (`theta`) poll tick otherwise.

Each active dispatcher–poller independently maintains its canonical cursor `C`
and its run-level epsilon cursor `E`.

## Dispatcher identity and top-down orchestration

Every highest-façade dispatch requires a non-empty `identity_id`.

That value identifies the higher-application actor, client, device, worker, or
other dispatcher principal associated with the action. It is not generated by
the controller and is not equivalent to `dispatch_id`.

The distinction is:

```text
dispatcher_identity_id
    Stable identity supplied by a higher application.

dispatcher_role
    Normalized role used for the dispatch, or JSON null for roleless dispatch.

dispatch_id
    Unique identity of one controller execution envelope.

event_id
    Unique identity of one emitted event packet.
```

One direct dispatch therefore produces:

```text
controller.loop.start
    dispatch_id = D
    dispatcher_identity_id = I
    dispatcher_role = R

controller.loop.end
    dispatch_id = D
    dispatcher_identity_id = I
    dispatcher_role = R
```

The actor fields are immutable across the envelope.

Identity validation occurs before role authorization, target resolution,
staleness classification, controller entry, canonical event emission, and
callback invocation. A missing or blank identity therefore produces no
controller or datum event.

The core records identity for orchestration and audit correlation. It does not
yet claim identity ownership, authentication, authorization, delegation, or
server-side actor isolation. Higher hosting applications may use the recorded
identity to implement those policies.

A future server ownership rule can therefore reason over facts such as:

```text
dispatcher_identity_id owns session access handle H
dispatcher_identity_id may act under dispatcher_role R
dispatcher_identity_id may mutate target T
```

without changing the controller event grammar.

## FunkTM-generated dispatcher identity

The first action of a FunkTM chain is the caller's manual dispatch and retains
the caller identity unchanged.

For every generated continuation:

```text
dispatcher_identity_id =
    funkedauto-{generated-role-name}-{initial-manual-identity-id}
```

A roleless generated continuation uses:

```text
funkedauto-roleless-{initial-manual-identity-id}
```

For example:

```text
initial manual actor:
    dispatcher_identity_id = browser-tab-17
    dispatcher_role = writer

generated auditor continuation:
    dispatcher_identity_id = funkedauto-auditor-browser-tab-17
    dispatcher_role = auditor
```

Every generated identity derives directly from the initial manual identity.
Generated identities are never recursively prefixed.

This makes the causal origin visible while still distinguishing generated
role-bound actors from the manual dispatcher.

The highest `_thinksessions.run.run_from_here` façade resolves the dispatch’s canonical
write targets and compares C with the latest canonical event sequence. For a
dispatch targeting T datums, this check is O(|T|), does not scan the event
queue, and does not depend on the width of (C, A].

Role authorization is evaluated first. Fill and signal datum ids enter the same
write-guard and conflict-target resolution path.

A stale cursor is not automatically rejected merely because the canonical
sequence advanced. A stale dispatch remains valid when the active write scope
has not changed and none of its targeted datums successfully changed after C.

Highest-façade decision:

```text
C omitted    ──► unchecked compatibility allow
C malformed  ──► reject invalid_event_cursor
C > A        ──► reject future_event_cursor
C = A        ──► allow at_high_water

C < A:
active scope changed after C
    ──► reject stale_scope_changed

a submitted target changed after C
    ──► reject stale_conflict

otherwise
    ──► allow stale_but_disjoint
```

C is an exact non-negative integer contract. Numeric strings and floats are
malformed rather than coerced.

`stale_scope_changed` has precedence over `stale_conflict`. A cursor that
predates movement to another form/frame/span is not allowed to address the new
surface by reusing an old datum id.

Dispatch response terminology is also deliberate:

```text
applied=True
    The request entered controller execution.

write_committed=True
    The submitted target set committed.

dispatch_outcome="semantic_rejected"
    The request was admitted but not committed.

dispatch_outcome="system_error"
    The request was admitted but terminated by a bounded systematic
    controller failure.

dispatch_outcome="stale_rejected"
    The request was rejected before controller entry.
```

Accepted fills and accepted signals update the same target index. A signal for
datum d therefore makes an older fill for d stale, and vice versa.

A stale, future, or malformed rejection occurs before controller entry. It
therefore emits no controller event, no datum event, and no new canonical event
sequence.

An unauthorized fill or signal raises the established `PermissionError`
contract before the caller receives any staleness classification.

## Controller action-envelope safety law

Once `controller.loop.start` has been successfully recorded in the canonical
queue, every ordinary in-process Python `Exception` raised during controller
routing, liaison execution, U recovery, or result construction is converted
into one matching `controller.loop.end` packet with:

```text
payload.outcome = "system_error"
payload.system_error.kind = "controller_dispatch_system_error_v1"
```

Callback exceptions are isolated after canonical queue insertion and cannot
break canonical event recording.

“Trident” is useful shorthand for:

```text
controller start
    + zero or more informative events
    + matching controller end
```

It is not a literal three-event requirement. Informative events may be absent,
may be numerous, and may also occur between controller envelopes.

The guarantee is safety, not eventual liveness. It excludes `BaseException`
classes (`SystemExit`, `KeyboardInterrupt`), hard process death, machine loss,
and canonical sink failure. A sink may commit and then raise, so end delivery is
attempted once and never retried as a competing packet. A later controller start
allows a downstream projector to classify an older still-open envelope as
interrupted; merely being caught up while an envelope is open does not prove
interruption.

Only controller events are required to carry complete `U`. Datum lifecycle and
external events are informative and need not carry `U`, `dispatch_id`, or
dispatch actor identity. The latest known complete frontend state is therefore
the `U` on the latest controller event in the retained/replayed stream, not
necessarily the payload of the latest event of any kind.

The latest event packet is therefore **not** always a state description. It may
be an informative datum/external event. Frontends must track `latest_U`
independently from their canonical cursor.

A normal in-process controller dispatch is represented by one controller start,
zero or more informative events, and one matching controller end. Start and end
share `dispatch_id`, `dispatcher_identity_id`, and `dispatcher_role`, while each
event has its own immutable `event_id` and strictly increasing canonical
`event_seq`.

Informative events emitted while no controller action is open are valid
orphan or between-envelope events.

Semantic rejection is not a systematic controller error. It is represented by
a successful controller end whose `payload.result.last_error` is populated.

## Hosting-visible run-level epsilon (`eps`) channel

The canonical queue (`theta`) remains committed session truth. A multi-process
hosting transaction must not expose transaction-local queue positions through
the ordinary canonical polling route before commit.

A hosting adapter routes the explosion callback stream (`threaded_callbacks`)
into a separate, append-only, run-level epsilon (`eps`) log (`EpsLog`).

That log uses the callback seam already threaded through direct and
FunkTM-generated dispatches (`explosion_events_callback` +
`controller_events_callback` + `observe_dispatch_context_v1`).

Its sequence is:

```text
eps_seq (run-scoped, strictly increasing per run)
```

not:

```text
event_seq (canonical theta sequence)
```

Each `eps` row carries causal lineage linking it to `theta`:

```text
theta_event_seq_at_emit
emitter_origin        (widget_explosion | funk_filler | controller_hook | session_bootstrap | ambient_service)
trident_dispatch_id
```

Consequences:

* pollers and dispatchers may see live datum explosions on `/eps/` while a
  durable dispatch transaction is still open (via an autocommit side-channel
  connection on multi-process Django hosting);
* visibility (`owner-only` vs `all-with-modulation`) and static datum role-read
  modulation (`required_roles`) are enforced at read time;
* rollback of the outer dispatch transaction leaves already-emitted `eps` rows
  intact in the append-only `eps` log, while `theta` does not advance; a
  frontend comparing `row.theta_event_seq_at_emit` against `theta`'s
  `session_latest_event_seq` can distinguish live/uncommitted emissions from
  committed history;
* the canonical (`theta`) poller remains completely independent of `eps_seq`.

The same callback mapping is retained throughout a complete FunkTM chain.
Every generated direct dispatch therefore records its explosion events into the
run-level `eps` log with exact per-hop attribution (`observe_dispatch_context_v1`).

For local Flask hosting, `InMemoryEpsLog` provides the process-local `EpsLog`
implementation. For Django service hosting, `RunEpsMessage` + `RunEpsCursor` on
an autocommit connection alias (`eps_log`) provide the durable/TTL PostgreSQL
implementation without requiring Redis for `eps`.

The clean separation is:

```text
epsilon (eps)
    live, run-scoped (eps_seq), append-only, visibility + role-modulated,
    causally linked via (theta_event_seq_at_emit, emitter_origin, trident_dispatch_id)

canonical events (theta)
    committed, session ordered (event_seq), role projected, cursor authoritative
```

## Frontend modulation: canonical events to action envelopes

A frontend may incrementally derive a compact Markovian projection:

```text
canonical event queue
    -> ordered controller action envelopes
    -> latest_U + open envelope + completed action history
```

For each controller start:

1. update `latest_U` from `payload.U`;
2. require non-empty `dispatcher_identity_id` and a string-or-null
   `dispatcher_role`;
3. if another envelope is open, close that older local projection as
   `interrupted`;
4. open a new envelope keyed by `dispatch_id`, retaining the actor fields.

For each informative event:

* attach it to the currently open envelope when one exists;
* otherwise retain it as a between-envelope/orphan informative event.

For each controller end:

1. update `latest_U` from `payload.U`;
2. match by `dispatch_id`, `dispatcher_identity_id`, and `dispatcher_role`;
3. classify as:

   * `system_error` when `payload.outcome == "system_error"`;
   * `semantic_rejected` when `payload.result.last_error` is non-empty;
   * `success` otherwise.

The derived envelope is a frontend projection, not a replacement canonical
record. Informative events do not currently carry `dispatch_id` or dispatcher
actor identity; attachment to an open envelope is therefore temporal
attribution, not an independent causal identity guarantee.

The following transition rule holds for ordinary controller-mediated movement
with no out-of-band session mutation:

```text
previous controller end U == next controller start U
```

A new frame/span reached by dispatch is first visible on that dispatch's end
`U`, not its start `U`. This is intentionally scoped: bounded-window gaps,
out-of-band state mutation, or role-different projections invalidate a blanket
byte-equality claim.

Initial and terminal edges are ordinary envelopes:

```text
ATSTART -> first renderable/manual state
last renderable/manual state -> ATCOMPLETION
```

The in-core canonical queue is bounded. “Forward-only” means event sequence and
history order never reverse; it does not mean every event is retained forever.
Applications requiring complete audit history must durably persist canonical
events outside the bounded live queue.

⚠ DANGER — REQUIRED MULTI-PROCESS SERVER RESPONSIBILITY ⚠

The highest façade supplies an exact process-local serialized boundary for
every dispatch that enters through `_thinksessions.run.run_from_here` in that process.

That process-local lock is not a distributed transaction.

When multiple server or worker processes can dispatch the same session, all
such writes must additionally pass through one distributed per-session write
boundary: a repository transaction, compare-and-swap operation, distributed
lock, session actor, queue, or equivalent mechanism.

That distributed boundary must span:

```text
1. loading canonical high-water A and the staleness index;
2. validating caller cursor C;
3. executing the dispatch or complete chain reaction;
4. assigning and committing canonical event sequences;
5. updating target and scope change indexes;
6. committing the session mutation and indexes together.
```

Without that primitive, two processes can both observe the same A and both pass
validation before either commits. One commit can then make the already-validated
second dispatch stale.

Persisting a last-changed field without an atomic transaction does not solve
this race.

Application responsibility: choose a suitable polling cadence, consume
events in canonical order, maintain C correctly, and include C with each checked
dispatch.

Single-process hosting responsibility: route dispatches through
`_thinksessions.run.run_from_here`, whose per-session reentrant lock serializes the
highest-façade check and dispatch path within that process.

Multi-process hosting responsibility: provide the additional distributed
per-session transaction or compare-and-swap boundary described above. The core
does not claim to solve this race.

Identity ownership remains a hosting responsibility.

Recording `dispatcher_identity_id` does not authenticate it. Public servers
must derive or validate identity from their authenticated access/session
boundary rather than trusting arbitrary unverified browser text. The identity
passed into `_thinksessions.run.run_from_here` should already be the server-approved
dispatcher identity.

## Why this scales

Steady-state polling returns only the latest sequence integer A, not session
state or an event collection, so each unchanged poll has a small and bounded
response size. Full event retrieval occurs only after the integer changes.

Load scales primarily with the number of currently active
dispatcher–pollers and their configured polling frequencies, not with the
total number of registered users, dormant clients, or historical participants
in a session. Inactive pollers generate no polling traffic.

Capacity can therefore be tuned centrally through four explicit controls:
baseline canonical period B, local-dispatch period/window D/WD,
foreign-activity period/window R/WR, and in-flight epsilon period P (250 ms
while a local dispatch is in flight; piggybacking on canonical ticks otherwise).
The canonical modes are bounded and do not self-refresh from every page.

```text
Many-session engine view
server router
│
├─ session A ─► one serialized write lane
│                 ├─ dispatcher A1 / poller A1 / cursor C_A1
│                 ├─ dispatcher A2 / poller A2 / cursor C_A2
│                 └─ canonical A_A, queue Q_A, S_A, L_A(t)
│
├─ session B ─► one serialized write lane
│                 ├─ dispatcher B1 / poller B1 / cursor C_B1
│                 └─ canonical A_B, queue Q_B, S_B, L_B(t)
│
└─ session N ─► one serialized write lane
                  └─ independent canonical state
```

Different sessions may execute concurrently. Writes for the same session must
be sequential. Pollers remain independent even when they view the same session:
each owns its own C, role, identity, retry policy, and local rendering state.

Every poller for one session ultimately advances through the same canonical
sequence positions, although role projection may omit event bodies.
`next_after_event_seq` allows a restricted poller to advance across those
hidden positions without learning their contents.

`identity_id` is mandatory for dispatch and pull. Dispatch identity is copied
onto controller events. Pull identity remains stateless caller correlation and
does not create a server-side receiver registry.

The retry builder is intentionally invoked again after catch-up. Replaying a
payload created from an old shell defeats the purpose of staleness prevention.

## What the single-process E2E proves

The highest-façade E2E sheet proves, using only Python calls and no server:

* sparse scalar polling while idle;
* bounded inner event catch-up after movement;
* canonical order and hidden-position advancement;
* immediate high-alert polling after a client's own dispatch;
* accepted fills advancing the target frontier;
* accepted signals advancing the same target frontier;
* eventless stale/future/malformed rejection;
* refresh-and-retry success from a new cursor;
* independent cursors for multiple clients;
* independent queues and stale indexes for multiple sessions.

It deliberately does not prove multi-process exclusion, crash atomicity,
session migration, or distributed retry ownership. Those remain hosting-server
obligations.

Server-boundary E2E sheets additionally prove:

* Flask and Django expose the same run-level `/eps/` contract (`EpsLog`);
* datum explosion events can be read on `/eps/` while a dispatch remains in flight;
* `owner-only` channels are hidden from role-sealed pollers;
* `all-with-modulation` channels enforce static datum role-read modulation;
* `eps` rows carry `eps_seq`, `theta_event_seq_at_emit`, `emitter_origin`, and `trident_dispatch_id`, and never carry canonical `event_seq`;
* direct and generated chain controller envelopes remain balanced on `theta` while their explosion events are attributed per-hop on `eps`;
* canonical (`theta`) polling behavior remains unchanged.

## Recommended two-loop client pattern

```python
C = persisted_or_initial_cursor
E = persisted_or_initial_eps_cursor
dispatch_until = 0
remote_until = 0
dispatches_in_flight = 0

while client_is_active:
    now = monotonic_ms()

    if dispatches_in_flight > 0 or now < dispatch_until:
        canonical_delay = 5_000
    elif now < remote_until:
        canonical_delay = 15_000
    else:
        canonical_delay = 30_000

    A = get_live_session_latest_event_seq(
        session_id=session_id
    )

    if A > C:
        caught_controller_actors = set()
        caught_unattributable_movement = False

        while C < A:
            page = get_live_session_events_since(
                session_id=session_id,
                role=role,
                identity_id=identity_id,
                after_event_seq=C,
                limit=page_size,
            )

            apply_in_sequence_order(page["events"])
            classify_page_activity(
                page,
                caught_controller_actors,
                caught_unattributable_movement,
            )

            C = page["next_after_event_seq"]
            A = page["session_latest_event_seq"]

        if (
            caught_unattributable_movement
            or any(
                actor != identity_id
                for actor in caught_controller_actors
            )
        ):
            remote_until = max(
                remote_until,
                monotonic_ms() + 60_000,
            )

    # Piggyback eps catch-up on every theta poll tick:
    eps_page = get_run_eps(after_seq=E, limit=eps_page_size)
    apply_eps_rows(eps_page["rows"])
    E = eps_page["next_after_seq"]

    sleep(canonical_delay)
```

`identity_id` is mandatory for dispatch and pull. Dispatch identity is copied
onto controller events. Pull identity remains stateless caller correlation and
does not create a server-side receiver registry.

`next_after_event_seq` must be used rather than the final visible event's
sequence. A role-projected poller may have advanced through intentionally hidden
canonical positions.

After submitting a dispatch, a dispatcher enters the bounded local-dispatch
mode and runs the same canonical catch-up loop. While the dispatch is in flight,
the client polls `/eps/?after_seq=E&limit=L` every 250 ms; when no dispatch is
in flight, `/eps/` is polled as a piggyback step on each canonical (`theta`)
poll tick:

```text
E = latest consumed eps_seq for this run

while dispatch unresolved:
    eps_page = get_run_eps(after_seq=E, limit=eps_page_size)
    apply_eps_rows(eps_page.rows)
    E = eps_page.next_after_seq
    sleep(250 ms)
```

`eps` rows must never be passed to the canonical (`theta`) envelope projector.
Each `eps` row carries `theta_event_seq_at_emit`, `emitter_origin`, and
`trident_dispatch_id` so UI projections can correlate `eps` emissions with
`theta` controller tridents without conflating `eps_seq` and `event_seq`.

## Persistence law

The in-memory target-change index is process-local. The highest façade does not
independently choose a repository or perform implicit persistence I/O around
each dispatch.

This separation is required because the globally configured repository is not
necessarily the repository that owns a particular already-created concrete
session API. Unconditional persistence lookup from the façade can therefore
read the wrong repository.

Django owns restoration and persistence:

1. acquire the database row lock;
2. cold-load the locked authoritative session row;
3. enter the core process-local staleness boundary;
4. restore the stored target/scope snapshot;
5. invoke the normal highest-façade dispatch or complete chain dispatch;
6. force a complete opaque-runtime checkpoint, regardless of the session's
   ordinary core manual-I/O persistence policy;
7. verify that the checkpointed queue high-water has not regressed;
8. persist the new target/scope snapshot;
9. persist the immutable request receipt;
10. commit the transaction.

The complete opaque-runtime checkpoint is what makes the following one atomic
version:

```text
engine/program state
    + retained canonical event queue
    + next canonical event sequence
    + latest canonical event high-water
    + target/scope staleness index
    + immutable request receipt
```

Per-event high-water updates may occur while the logical dispatch is still
running, but they are transaction-local intermediate writes. They do not
replace the final complete opaque-runtime checkpoint.

If any step fails, Django must both roll back the database transaction and
completely invalidate the process-local runtime representation. Selectively
clearing known cache dictionaries is insufficient as a formal guarantee.

Before the next coordinated mutation, the service verifies:

```text
cold-restored runtime canonical high-water
    ==
locked ThinkumentSesh.latest_event_seq
```

Any mismatch fails closed before controller entry.

Before transaction commit, the service additionally requires:

```text
checkpointed opaque runtime canonical high-water
    ==
ThinkumentSesh.latest_event_seq
```

This prevents a server from committing a new scalar cursor while retaining an
older engine blob whose queue would later restart or regress sequence
assignment.

A hosting service that does not perform this protocol retains process-lifetime
staleness indexes and must not claim restart-safe or multi-process dispatch
coordination.
